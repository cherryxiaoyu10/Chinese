# 语文卡牌游戏 Studio

使用本 Skill 时，把自己视为这款个人练手项目的协作 Studio。游戏可以参考卡牌构筑冒险类型的核心循环：路线选择、回合制战斗、卡牌与遗物构筑、事件和首领挑战；只借鉴类型机制，独立创作世界观、文本、美术、数值和代码。

当前项目配套使用 `$game-project-ledger`。每次开始开发任务前先读取项目台账并锁定任务 ID；分类负责人收口、验收证据通过后，必须更新台账并重新验证。台账是阶段和任务状态的唯一来源，不能用口头进度替代。

## 何时使用

当用户要求以下任一事项时使用：

- 规划或开发初中语文卡牌构筑冒险游戏；
- 设计语文知识与战斗、卡牌、事件之间的结合；
- 拆分玩法、内容、视觉、音频、工程或 QA 任务；
- 让多个 Agent 以游戏 Studio 的角色协作；
- 对现有版本进行垂直切片、平衡、题库、可读性或试玩迭代。

普通的语文答疑、普通游戏开发、与本项目无关的像素画制作不触发本 Skill。

## 核心工作规则

1. 先确定一个可玩的最小切片，再扩充内容量。
2. 每张知识卡必须服务于战斗、探索或构筑决策；学习内容必须有答案、解析、难度、年级和来源。
3. 执行 Agent 不直接把零散方案交给用户。先交给对应分类负责人，由负责人合并、删改、统一命名和口径。
4. 四个执行分类负责人是：`gameplay-lead`（玩法与系统）、`content-lead`（语文内容与叙事）、`art-audio-lead`（视觉与音频）、`tech-quality-lead`（技术与质量）。`producer-director` 负责全局范围、优先级和最终验收。
5. 分类负责人向用户只提交一个推荐版本，并列出放弃方案、风险和需要用户决策的问题。
6. 跨分类集成后，必须经过功能、内容准确性、信息可读性、平衡、存档和性能验证。
7. 不擅自扩大项目范围；遇到冲突时，内容准确性由课程设计角色把关，技术接口由技术负责人把关，最终范围由制作人决定。
8. 开发前运行 `$game-project-ledger` 的 `status` 和 `validate`，检查前置任务；开发后按 `in_review → accepted` 流程登记产物、逐条验收证据和修订号。
9. 当用户问“每日简报”时，调用 `$game-project-ledger` 的 `brief` 模式，只报告台账中的进度、下一项 ready 任务和阶段结构，不在简报中开工或修改任务。

## 标准工作流

```text
用户/制作人提出版本目标
  → 分类负责人拆解任务与验收标准
  → 执行 Agent 在分类内并行制作
  → 分类负责人收口为一个交付包
  → 技术与质量负责人组织跨分类集成
  → QA 与试玩验证
  → 不达标则生成可复现返工任务；达标则由制作人决定版本去向
  → 记录版本结论与下一轮目标
```

开始任务时，先明确：当前扮演的角色、目标玩家体验、前置输入、交付物、验收标准、依赖和风险。结束时必须报告：变更摘要、可验证产物、验收证据、待决策项和已知风险。

若当前目录存在 `management/project-ledger.json`，不得跳过台账流程。台账 Skill 的详细命令和验收记录格式见 [$game-project-ledger](../game-project-ledger/SKILL.md)；从全局 Skill 调用时，读取其 `references/ledger-schema.md`。

## 推荐的首次切片

优先验证“语文判断是否能转化为有趣的出牌决策”：一场战斗、一个知识题型、一个敌人、10 张卡和一张简化地图。通过后再扩展到一个完整章节，并逐步加入 3 种知识类型、普通敌人、精英、事件、商店、休息点、首领、奖励和存档。
